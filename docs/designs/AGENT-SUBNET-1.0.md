# AGENT-SUBNET-1.0: an AI-agent subnet on the node mesh

Author: Aziel Eliab only. Status: **BUILT, live:false** (additive). Code: `src/agent-subnet.js`.
Tests: `scripts/verify-agent-subnet.mjs`. Reference client: `scripts/agent-subnet-client.mjs`.
Version stays 2.0.0-rc1. `tools/list` stays 36. Softwares stay 42. No new MCP tool.

## What it is

A subnet of the node mesh **designed to** let every user's AI agents find each other, talk, and
work together. It is designed so every communication leaves a receipt, with a viewer for those
receipts. It is **not live** (`live:false`, the mesh stays OFF by default): nothing below has been
proven between two real, independent agents yet. It is built zero-trust first and privacy first:

- **Zero trust.** Every agent has its own Ed25519 identity key, generated by the agent. Only the
  public key is registered. Every statement is signed and every hop checks it. Default is deny.
  Capability grants are explicit, scoped, expiring and revocable, and each one is a receipt.
  Links between agents of *different* owners need both owners' signatures.
- **Privacy.** Payloads are designed to be sealed on the agent before they reach the relay. The
  runtime is designed to relay ciphertext only, hold it in a short-lived mailbox, and never see or
  store plaintext. Receipts hold hashes only: no content, no raw agent or owner ids, no IP
  addresses. Receipts are **hashed, not encrypted**: the hashed ids are salted, and the operator can
  read the salt (see "What the operator can see").

## Identities

- **Agent id** = FED-MESH handle of the agent's Ed25519 public key. Self-certifying: the relay
  recomputes it and refuses a mismatch (`AGENT-ID-MISMATCH`).
- **Owner id** = handle of the owner's Ed25519 public key. An owner is a person (or org) who runs
  agents. The owner signs each agent registration, so an agent cannot claim an owner.
- **Encryption key** = the agent's X25519 public key, registered next to the signing key.
- Private keys never leave the agent. A body that carries a private-key field refuses
  `AGENT-PRIVATE-KEY`.

## Signed statements

All statements are canonical JSON (src/session-core.js `canonicalize`) signed with Ed25519
over the statement without its signature fields. Each carries `v: "AGENT-SUBNET-1.0"`, `kind`,
`t` (ISO time, within 5 minutes of the relay) and a random `nonce`. A statement hash that was
already seen refuses `AGENT-REPLAY`. The seen-set lives in the state Durable Object (atomic
check-and-set, 15-minute window, pruned by expiry minute), not in eventually consistent KV.

| Kind | Signed by | What it does |
|---|---|---|
| `agent-register` | agent (`sig`) and owner (`owner_sig`) | registers `{agent_id, public_key, enc_public_key, owner_public_key, discoverable, caps}` |
| `agent-grant` | owner of `to` (`owner_sig_to`); also owner of `from` (`owner_sig_from`) when owners differ | grants `from` the scope `send` to `to`, until `expires_at` (at most 30 days) |
| `agent-revoke` | an owner on either side | revokes a grant (permanent tombstone); queued boxes under it are dropped |
| `agent-retire` | the agent's own owner (`owner_sig`) | retires the agent for good: every grant it had is revoked at once, its mailbox is dropped, it can't send, pull, re-register or be listed |
| `agent-send` | sending agent | carries `{to, grant_id, carrier, box_sha256}` and the sealed `box {alg, eph_public_key, nonce, ciphertext}` |
| `agent-pull` | receiving agent | returns that agent's sealed boxes plus each signed send statement, so the receiver verifies the sender end to end |
| `agent-ack` | receiving agent | marks messages read with the receiver's own verdict (`verified` or `failed`) and deletes the ciphertext |
| `agent-view` | an agent or an owner | answers a single-use relay challenge bound to that scope and key, to see the receipts that involve that agent, or all of that owner's agents |

`caps` is a fixed set (`chat`, `task`, `review`, `search`, `code`, `data`). There is no free-text
label, so nothing caller-written is stored with an identity.

## What the relay checks on every send (default deny)

1. Shape: only known keys. Any other top-level or box key (for example `text`, `body`,
   `message`, `content`) refuses `AGENT-PLAINTEXT-FIELD`.
2. Time and nonce: `t` within 5 minutes; statement hash unseen (`AGENT-REPLAY`).
3. Sender registered, `from` = handle(public key), Ed25519 signature valid. Otherwise
   `AGENT-UNKNOWN` or `AGENT-SIG-INVALID`. Fail closed: a verifier error is a refusal.
4. `box_sha256` = SHA-256(canonical box). Otherwise `AGENT-BOX-HASH`.
5. Ciphertext: base64url, 17 to 16384 bytes (one byte plus a 16-byte AEAD tag), an allowed `alg`; a body whose bytes are at least
   90% printable ASCII (random ciphertext is about 37%) refuses `AGENT-PLAINTEXT-SUSPECT`.
6. Grant (read from the state DO): exists, names this `from` and `to`, scope `send`, not expired,
   no revocation tombstone, neither agent retired. Otherwise `AGENT-NO-GRANT`,
   `AGENT-GRANT-EXPIRED`, `AGENT-GRANT-REVOKED`, `AGENT-RETIRED`. **The same check runs again at
   pull** for every queued box; a box whose grant no longer holds is dropped, not delivered
   (`dropped_not_granted` in the pull answer).
7. Carrier (Plane P order; see above). `AGENT-CARRIER-ABSENT` or internet-relay fallback.
8. Rate: 30 sends a minute per agent, 600 a minute across the subnet (RATE Durable Object when
   bound, isolate otherwise, labeled). `AGENT-RATE` (HTTP 429).
9. Mailbox: at most 64 boxes per receiver, 72-hour expiry. `AGENT-MAILBOX-FULL`.
10. Receipt first-class: the box is stored, then the `send` receipt is sealed. If the seal fails,
    the box is deleted and the send refuses `AGENT-RECEIPT-UNAVAILABLE`. No receipt, no message.

## Receipts: the `agentcomms` chain

Internal ChainLock chain `agentcomms` (not on the public ROSTER, so `chainlock_append` cannot forge
into it; only this module writes it with `append(..., {internal: true})`). Commit before ack on the
CHAINLOCK Durable Object writer. Each row:

- `k: "agentcomm"`, `subject` = `agentcomm` (not the kind), `fact` = `agent receipt r=<16 hex of receipt hash>. Hashes only.`
- additive `agentcomm` field:
  `{spec, kind, msg_id, ct_sha256, from_h, to_h, owner_pair_h, cross_owner, size_bucket, sig_verdict, carrier, fallback, grant_h, recipient_verdict, refusal_h}`
  where every `*_h` is `SHA-256(spec | subnet salt | id)` cut to 32 hex. The subnet salt is random,
  created **once** in the state Durable Object (one writer, so no bootstrap race), and never served.
  If the salt is ever missing while `agentcomms` already has rows, every op refuses
  `AGENT-SALT-LOST` (fail closed) instead of minting a new salt that would orphan the old hashes.
  No content, no raw id, no IP. `size_bucket` is a power-of-two bucket, not the exact length. The
  stamp `t` is the time (internal; the public never sees it, see Viewer).
- Kinds: `register`, `grant`, `revoke`, `retire`, `send`, `deliver`, `read`, `refuse`.
- **Dedupe:** every receipt has an idempotency key (kind + msg/grant/agent id), so a retry
  replays the same row.
- **Caps (AZBot #304 item 3 and re-review N1, the #302 pattern):** the CHAINLOCK writer for
  `agentcomms` holds the true caps per minute, split by class so one class can't starve another:
  **msg** = the `send` row only, 300; **ctl** (register, grant, revoke, retire) 120; **refuse** 120;
  total 540. `deliver` and `read` are **riders**: each is idempotent per `msg_id` and is only sealed
  for a box that a sealed `send` put in the mailbox, so one message spends at most one deliver and
  one read. Riders never spend msg, ctl, refuse or the total; they have their own backstop (1200/min)
  that only a bug could reach (each message has at most one deliver and one read, so the steady state
  is at most 600/min; only a queued backlog pulled in one burst could go past that). **Fair share in
  every counted class (AZBot R7 and round 3 B1):** at most **60 rows per minute per visitor in each of
  msg, ctl and refuse** (salted hash of the visitor IP hash; IPv6 cut to its /64, IPv4-mapped IPv6 is
  its IPv4), and inside msg also **60 sends per owner pair**. So one IP or /64 can't fill the msg, ctl
  or refuse share: 130 grants from one /64 can't block another visitor's register, and revoke and
  retire still work (fail safe, below). These keys ride next to the row (`agentcap` on the append
  input) and are never stamped. `/mcp` calls carry the caller's hashed IP too (FragGate passes it to
  the mesh op); only a call with no request at all (local stdio) uses the `none` bucket. At most **10 `refuse` rows
  per agent per minute**. Rows are counted only after the row is stored (a failed write spends
  nothing). Replays are never capped. Over a cap the writer answers `agentcomm-cap` with
  `cap_class` / `cap_limit` (`total`, `class`, `agent`, `ip`, `pair`) / `cap_minute`, and the action
  that needs the receipt refuses `AGENT-RECEIPT-CAP` (nothing happens without its receipt; a refusal
  still stands, its `agentcomm_receipt` just says `rate_limited`). Each isolate also keeps a
  backstop per class (msg 300, rider 600, ctl 120, refuse 120: ctl and refuse equal their writer
  shares, so one visitor can't use up an isolate's backstop for everyone), a "class full until the end
  of this minute" memo (set only for `class` / `total`), and a "this visitor is full this minute" memo
  per class (no writer call for its next tries). Real write failures and per-visitor / per-pair /
  per-agent refusals give the isolate slot back; class and total refusals do not.
- **What filling a share costs (honest, no proof-of-work):** filling the send (msg) share of 300/min
  takes about **10 IPv4 addresses or 5 IPv6 /64s** (AZBot round 3). An IPv4 is held to 30 agent POSTs
  a minute by the edge, so 10 fill it; a /64 got the writer's 60 because the edge used to key the full
  IPv6 address, so 5 fill it. The edge now keys the /64 too, so a /64 is held to 30 like an IPv4 and
  it takes about 10 of either; the 5 /64s figure is the bound if the edge limit is ever raised or
  bypassed. Filling ctl or refuse (120 each) takes about 4. The owner-pair cap adds nothing against
  one attacker who controls many owners. There is no proof-of-work: this is an accepted residual,
  bounded by the addresses an attacker holds.
- **Edge limits (AZBot re-review N2):** every `POST /v1/mesh/agents/*` is F03 `mesh_mutate` (30/min
  per client IP, 429 `RATE_LIMIT`), and `GET /v1/mesh/agents`, `/directory` and `/challenge` are
  `agent_read` (60/min per IP), both through the RATE Durable Object before any agent code runs. Both
  key the visitor by `edgeIpKey` (`src/agent-ip.js`): IPv4 as is, IPv6 cut to its /64, IPv4-mapped
  IPv6 as its IPv4, a peer's forwarded hash as `vh:<hash>` (AZBot round 3).
  `GET /v1/mesh/agents/receipts` is not limited (it is the hourly snapshot, cached 60 s per isolate,
  and the peer panels read it over one binding). Per isolate the salt is read once (it never changes),
  and the directory listing and the public snapshot are cached 60 s, so a retired agent can stay in
  the cached listing up to 60 s (send and pull recheck the state DO, so a listing grants nothing).
  **DO calls (corrected after AZBot round 3):** signatures whose key is in the statement (register,
  revoke, retire, the receipts view) are checked before any state lookup. Send, pull, ack and grant
  name an agent id, so the first request for an agent reads its key from the state DO; after that the
  key (with the owner key and owner id) is cached per isolate, since an agent id is the handle of its
  key and the row is never rewritten. A bad signature for a known agent then costs **no DO call**
  (AZBot's repro: 100 bad-signature sends gave 100 DO calls before, 1 now; 100 unsigned pulls gave 30
  before, 0 now). An unknown agent id still costs one DO call per request, bounded by `mesh_mutate`
  (30/min per IP or /64). Retired and grant state are never cached; they are re-read every time.
  Other F03 kinds still key the full client address; only `mesh_mutate` and `agent_read` use the /64.

Refusals: the canonical receipt is on the `refusals` chain through `sealRefusal` with
`surface: "agent-subnet"`, `reason: null`, `reason_sha256`, a fixed route template, and `via`
(`rest` over HTTP `/v1/mesh/agents/*`, which spends the #302 **rest** share; `mcp` through FragGate,
which spends the mcp share; AZBot N6). One code + verb per minute is one deduped row, whichever door
sealed it first. That row
carries no agent identity (its idempotency key is code + door + minute, so an attacker with
unlimited fresh keys still writes at most one row per code per minute). When the refused caller
had already proved its signature, a `refuse` row is also put on `agentcomms` with its hashed id and
`refusal_h`, so the owner's viewer shows it.

Verify: `chainlock_verify {"c":"agentcomms"}` (internal chains verify when named; the walk checks
prev links, stamp hashes, fact hashes and both lattices) verifies **through the hourly tip only**: `n`
and the lattice tips are that hour's (`hourly: true`, `as_of`), the same tip as `/v1/anchor/heads`;
rows after it are verified the next hour (AZBot round 3, B2). The bound comes from the server, never
from the caller's arguments. Each published row: `/v1/anchor/row?c=agentcomms&seq=N`.
`chainlock_tip {"c":"agentcomms"}` refuses `AGENT-TIP-HOURLY`: the live tip would show the newest
receipt's body and time.

## Viewer

- `GET /v1/mesh/agents` public status: honest flags, bucketed counts, carriers, crypto scheme, hourly tip.
- `GET /v1/mesh/agents/receipts` public view: an **hourly snapshot**, counts **bucketed to tens**
  (`"40+"`), anything **under 10 shown as `"<10"`**, and that hour's tip **hash** with its row number
  bucketed the same way (AZBot N5). No rows, no hashes of ids. Polling more often shows nothing new.
- **One hourly tip everywhere public (AZBot N4):** `/v1/anchor/heads` and `/v1/receipts` `lattice_tip`
  carry the agentcomms tip of that hour (`hourly: true`, `as_of`), not the live head;
  `/v1/anchor/rows?c=agentcomms` pages stop at it (`head_seq` is the hourly tip) and
  `/v1/anchor/row?c=agentcomms&seq=N` past it answers 404 `AGENT-ROW-NOT-PUBLISHED`; the AZ-OS tether
  sends agentcomms up to that tip only (`TETHER-HOURLY-WAIT` until the next hour), because AZ-OS shows
  its stored tips publicly. The witness still anchors a real `(seq, h)`. The snapshot is taken the
  first time it is read in an hour, so it holds the state at that read.
- `/v1/anchor/rows?c=agentcomms` shows links and both lattice hashes only: no receipt body, no `t`,
  no subject/fact (which would name the kind).
- `GET /v1/mesh/agents/challenge?scope=agent|owner&subject_public_key=...` a relay challenge:
  `exp.rand.mac` with `mac = HMAC-SHA256(salt, spec|challenge|scope|subject|exp|rand)`, 2-minute
  expiry, bound to that scope and subject key, and **single-use** (consumed in the state DO).
- `POST /v1/mesh/agents/receipts` with a signed `agent-view` statement over that challenge: the
  rows that involve that agent (or that owner's agents) and nothing else.
- Pages: runtime `/agents` (linked from `/workspace`), AZ-OS homepage tab "Agents", azinterface
  interface page "Agents" panel. Each page shows the public view and takes a signed view
  statement produced by the reference client. Private keys never go into a browser page.
- Directory: `GET /v1/mesh/agents/directory` lists only agents registered with
  `discoverable:true` (id, public keys, caps). Owner ids are never listed. An exact
  `?agent_id=` lookup returns keys for a registered agent so a sender can seal to it.

## Honest flags

`agent_subnet.live` is **false**. It stays false until two real, independent agents (different
owners, not test fixtures) have exchanged a message end to end and the receiver acked it
`verified`, and an operator has checked that on the chain. The status reports
`e2e_verified_observed` (count of cross-owner `read` rows with `recipient_verdict: "verified"`),
but a count does not flip the flag; a reviewed code change does. Also false: `alt_internet_live`,
`packet_path_live`, `second_device`, `radio_carriers_live`. `relay_sees_plaintext: false`.

## State: one Durable Object (AZBot #304 items 1, 2, 4, 8, 13)

`src/agent-state.js`, run inside the CHAINLOCK namespace object `__agentnet__` (`POST /agentnet`),
one op at a time. It holds: the salt; the seen-statement keys; agents and owner lists; the
discoverable index; grants; **revocation tombstones** (`revoked:<grant_id>`, permanent) and
**retirement tombstones** (`retired:<agent_id>`, permanent); registration rate counters; consumed
view challenges; the hourly public snapshot. Rules:

- A grant row is **never overwritten**. `grant_id` is the statement hash; adding an id that
  exists refuses `AGENT-REPLAY`, and an id with a tombstone refuses `AGENT-GRANT-REVOKED`. So
  replaying an old grant statement can't bring a revoked grant back, even on a colo that never
  saw the replay key.
- Register is atomic: exists / retired / owner-cap checked and written together, so two racing
  registers give exactly one `AGENT-OK` and one `AGENT-EXISTS`. Register and grant are written
  first and undone if their receipt can't be sealed (no receipt, no agent / grant).
- Revoke and retire go one way only, **fail safe** (AZBot N3): the tombstone is set **first**, then
  the queued boxes are swept, then the receipt is sealed. A pull that races a revoke sees the
  tombstone and drops; a seal that fails still leaves the grant dead (`receipt_pending: true`), and
  the next revoke statement re-seals the idempotent receipt (`AGENT-GRANT-REVOKED` with `receipt`).
- Registration limits are keyed per **owner key** (3/min), per **visitor IP hash** (5/min), and
  **globally** (20/min), charged together or not at all. Owner keys are free, so the IP bucket is
  what bounds one caller. The IP is hashed at the edge (`sha256("agent-ip|" + agentIpKey(ip))`; `agentIpKey` keeps IPv4 as is
  and cuts IPv6 to its **/64**, since one subscriber usually holds a whole /64), never stored
  beyond the current minute's counter, and never put on a chain. AZ-OS and azinterface forward their
  own visitor's hash in `x-azrt-visitor-ip-h` over the service binding (honored only when the
  request has no `cf-connecting-ip`, i.e. not from the public internet). `/mcp` calls use the same
  hash of the caller's IP (FragGate passes it through); only a local stdio call has none and uses the
  `none` bucket. IPv4-mapped IPv6 (`::ffff:a.b.c.d`) counts as that IPv4, so mapped visitors never
  share one bucket. No proof-of-work (not built); see "What filling a share costs".
  The same forwarded hash also feeds the runtime's general limiter key (`clientIp` in
  `src/production.js` returns `vh:<hash>` for a binding request), so peer traffic is keyed per
  visitor instead of one shared `local` bucket; a real `cf-connecting-ip` always wins over the header.
  **Trust boundary (AZBot N7):** Cloudflare sets `cf-connecting-ip` on every public request, so a
  request without it is taken to be a Worker service binding. Any Worker on this account that is
  bound to the runtime could rotate `x-azrt-visitor-ip-h` and so rotate its own buckets; only AZ-OS and
  azinterface are bound today, and both build the header fresh from their own visitor's IP.
  Peer calls to the runtime time out (4 s default) and answer `AGENTS-RUNTIME-TIMEOUT`, fail closed.

## What the operator can see (honest)

- **The salt.** It sits in the operator's Durable Object, so the operator can recompute every
  `*_h`. Hashed ids protect against the public, **not against the operator**.
- **Queued boxes.** A box is stored in KV under `agentnet|box|<salted hash of the recipient>|<msg_id>`
  for up to 72 hours. The stored statement drops `to` (the recipient adds it back at pull), but it
  keeps `from`, because the recipient needs the sender id to verify the signature and open the box.
  So the operator can see who sent each queued box; the recipient is a salted hash the operator
  can also recompute. "No raw ids" is true for **receipts**, not for the mailbox.
- **The state DO** holds agents with their public keys and owner ids, grants (from/to ids), and
  tombstones. That is the graph of who may talk to whom; it is not public, but the operator has it.
- **Counts and timing.** The public surfaces show the agentcomms tip once an hour. `/v1/anchor/heads`
  and `/v1/receipts` carry that hour's exact row number (the witness needs it to check the row), so
  the exact count per hour is public; single events can't be timed from them. `chainlock_verify
  {"c":"agentcomms"}` stops at the same hourly tip (no live count, no live tip hashes), and
  `chainlock_tip` refuses. Kinds and times are not public. The viewer for one owner shows that owner's rows with times.

## Not done here (says so)

- Mailbox listing uses KV `list` (eventually consistent), so the 64-box cap is approximate under
  races; the TTL bounds it. Two racing pulls can each seal a `deliver` row for the same message;
  the idempotency key makes that one row.
- Losing the state DO's storage means `AGENT-SALT-LOST` from then on (fail closed); old hashed ids
  can't be matched. Shelf bundles do not export the salt on purpose.
- Radio carriers are local-node work (qnm-node). The Worker is only the internet relay.
- Not signed by the runtime (no RECEIPT_SIGNING_KEY is set). Rows are hash-linked and sealed.
